ОПИСАНИЕ API ПОРТАЛА АПТЕКАМОС
Назначение файла: исходные данные для промта на реализацию обмена в другой конфигурации 1С.
Дата сборки: 2026-09-29.

В заказе покупателя есть поле ВидЗаказа. Для каждого портала будет создан свой вид заказа. В нем мы укажем 
поле Портал с типом перечисление эвВидыИсточниковЗаказа.
В виде заказа будет прописан перечен Статусов заказов а табличной части Состояния. 

Состояния заказов имеют код на партале. На каждом портале свой код статуса. 
Связь состояний заказа и значений кодов статусов заказа на портале задаются в регистре сведений: эв_КодыСтатусовПорталов,
где ВидСтатуса это состояние заказа покупателя. И вид источника заказа.

Результаты каждого HTTP запроса фиксируются в регистре сведений эв_ЛогиHTTPПорталов.

================================================================================
1. ОБЩИЕ СВЕДЕНИЯ
================================================================================

Портал: АптекаМос (перечисление эвВидыИсточниковЗаказа.АптекаМос).

Общий модуль для процедур обмена с АптекаМос: эв_ОбменСПорталамиАптекаМос.

Сценарии, которые нужно реализовать:
1) Полная выгрузка остатков и цен.
2) Инкрементальная выгрузка остатков и цен (только изменения).
3) Загрузка заказов с портала.

Смежный сценарий (нужен для замкнутого цикла):
4) Отправка статусов заказов (им же фактически подтверждается получение нового заказа).

Настройки — регистр сведений эвНастройкиAPIИсточникаЗаказов в разрезе источника заказов:

  Адрес        — базовый URL API без завершающего слэша
  Логин        — bilUserLogin для заказов и статусов
  Пароль       — bilUserPassword для заказов и статусов
  ЛогинФТП     — bilUserLogin для выгрузки цен/остатков (имя поля в 1С историческое, это не FTP)
  ПарольФТП    — bilUserPassword для выгрузки цен/остатков
  merchant     — внутренний id аптеки на портале (org_id / orgId), число в виде строки

Источник заказов (справочник эв_ИсточникиЗаказов):
  - Вид      = АптекаМос
  - Активный = Истина
  - Склад    — склад аптеки
  - ВидЦен   — вид цены для price

Проверка готовности (ДанныеПорталаКорректны) в исходном коде проверяет только:
  Логин, Пароль, merchant.
  Адрес, ЛогинФТП и ПарольФТП не проверяются, хотя без них обмен не работает.
  В целевой реализации проверять все шесть полей.

Формат обмена: JSON, UTF-8.
Content-Type: application/json (для остатков и заказов явно; для статусов заголовки в коде пустые,
КоннекторHTTP.POSTJson всё равно сериализует JSON).

Авторизация: логин и пароль в query (заказы) или в теле JSON (остатки, статусы).
Заголовков auth-token / merchant-code нет.

Идентификаторы:
  - org_id / orgId — числовой id аптеки (настройка merchant)
  - drug_id        — код ЕГК номенклатуры (Номенклатура.ор_ЕГК), пробелы удаляются, по возможности Число
  - item_id        — UUID номенклатуры 1С (XMLСтрока(Номенклатура))
  - orderNum       — номер заказа на портале (строка/число)


================================================================================
2. РЕГЛАМЕНТ И ТОЧКИ ВХОДА В 1С
================================================================================

2.1. Инкрементальные остатки + загрузка заказов
Регламентное задание: эв_ОбменОстаткамиИЗаказамиПорталов
Метод: эв_ОбменСПорталамиСервер.ВыполнитьИнкрементальныйОбмен
Расписание метаданных: каждые 120 секунд, с 08:00 до 23:30.
Выполняется только на боевой базе.

Порядок:
  1) эв_ОбменСПорталамиСервер.ВыполнитьИнкрементальныйОбмен → внутри ВыполнитьЗагрузкуЗаказовИзАптекаМос()
  2) эв_ВыгрузитьОстаткиЦеныНаПорталАптекаМос(Ложь)

2.2. Полные остатки
Регламентное задание: эв_ОбменОстаткамиПолнымиПорталов
Метод: эвОбменСПорталамиСобытия.ВыполнитьОбменСПорталамиПолная
Расписание метаданных: 23:35–23:45.
Вызов: эв_ВыгрузитьОстаткиЦеныНаПорталАптекаМос(Истина)

2.3. Очередь статусов
Регламентное задание: эв_ОбработкаОчередиСтатусовПорталов
Метод: ВыполнитьОбработкуОчередиСтатусовПорталов → ОтправитьСтатусЗаказаАптекаМос
Расписание: каждые 30 секунд, с 08:00 до 23:00.

Код статуса для портала берётся в регистре сведений: эв_КодыСтатусовПорталов,
Статусы отправляются через очередь в регистре эв_ОчередьОтправкиСтатусовЗаказов.

Текущий статус при успешной отправке на портал фиксируется в регистре эв_ИсторияСтатусовЗаказов.


================================================================================
3. ВЫГРУЗКА ОСТАТКОВ И ЦЕН
================================================================================

Процедура: эв_ВыгрузитьОстаткиЦеныНаПорталАптекаМос(ПолнаяВыгрузка)
Сбор данных: эв_ПолучитьОстаткиЦеныНаПорталАптекаМос

HTTP:
  POST {Адрес}/Price/WPrice/WimportPrices

Один и тот же метод POST для полной и инкрементальной выгрузки.
Различие — флаг isTransact в теле.

3.1. Тело запроса

{
  "bilUserLogin": "<ЛогинФТП>",
  "bilUserPassword": "<ПарольФТП>",
  "isTransact": 0,
  "prices": [
    {
      "org_id": "12345",
      "drug_id": 12345678,
      "item_id": "<UUID номенклатуры>",
      "item_name": "Нурофен 200 мг №20",
      "item_code": "01.03.2027",
      "price": 249,
      "qtty": 12,
      "reserv": 1
    }
  ]
}

Поля пакета:

  bilUserLogin     string   ЛогинФТП настроек (не Логин заказов).
  bilUserPassword  string   ПарольФТП настроек (не Пароль заказов).
  isTransact       number   0 — полная выгрузка «с очисткой» на стороне портала.
                            1 — инкремент (транзакционное обновление без полной очистки).
  prices           array    Массив позиций.

Поля позиции prices:

  org_id     string/number  merchant источника (id аптеки на портале).
  drug_id    number/string  Номенклатура.ор_ЕГК без пробелов. Если значение числовое —
                            приводится к Число, иначе остаётся строкой.
  item_id    string         UUID номенклатуры 1С.
  item_name  string         Наименование, СокрЛП.
  item_code  string         Необязательно. Срок годности характеристики,
                            формат dd.MM.yyyy. Поле добавляется, только если дата заполнена.
                            Имя поля на портале — код позиции, в 1С туда кладут срок годности.
  price      number         Цена целым числом (ЧИСЛО(10, 0)).
  qtty       number         Доступный остаток (КоличествоОстаток − РезервОстаток).
                            В отличие от МегаАптеки/Ютеки Цел() не применяется.
  reserv     number         Всегда 1.

Штрихкоды, производитель, серия в пакет АптекаМос не передаются.

3.2. Отбор строк

Доступный остаток по складу источника:
  ТоварыНаСкладах.Остатки, КоличествоОстаток − РезервОстаток >= 1.

Инкремент (ПолнаяВыгрузка = Ложь): в выборку попадают только пары
(Номенклатура, Характеристика), у которых остаток в снимке
эв_СвободныеОстаткиДляПорталаАптекаМос отличается от текущего учёта
(включая обнуление).

Полная выгрузка: все позиции с остатком >= 1.

Фильтр перед отправкой:
  Если Цена = 0 ИЛИ ор_ЕГК = "" — строка НЕ отправляется.
  Без кода ЕГК позиция на портал не выгружается.

Если prices пустой — HTTP-запрос не выполняется.

Цена: регистр ЦеныНоменклатуры по виду цен источника, МАКСИМУМ(Цена).
В запросе заложена особая логика для ценовой группы «ЭВАЛАР»:
  цена без характеристики; для остальных — цена с характеристикой.
В исходном тексте запроса ВТ_Остатки.ЦеноваяГруппа используется, но в ВТ_Остатки
не выбирается — это дефект исходника. В целевой конфигурации поле ЦеноваяГруппа
нужно добавить в временную таблицу остатков.

3.3. После HTTP 200

Регистр-снимок эв_СвободныеОстаткиДляПорталаАптекаМос обновляется так же,
как у МегаАптеки/Ютеки:
  полная — очистить регистр, записать ненулевые остатки;
  инкремент — точечно по ключу Номенклатура+Характеристика, ноль удаляет запись.

Неуспех (не 200 или исключение) — снимок не меняется.

3.4. Регистр-снимок эв_СвободныеОстаткиДляПорталаАптекаМос

Непериодический, независимый.
Измерения: Номенклатура, Характеристика.
Ресурсы:   Цена (15.2), ДоступныйОстаток (15.3).
Реквизит:  ДатаОбновления.


================================================================================
4. ЗАГРУЗКА ЗАКАЗОВ
================================================================================

Процедура: ВыполнитьЗагрузкуЗаказовИзАптекаМос
Разбор: ЗагрузитьЗаказыАптекаМосJSON

Отдельного URL «подтверждение получения» нет.
После разбора каждый загруженный заказ ставится в очередь статусов как «Новый»
(КПередаче) и уходит на портал через setOrders.

4.1. Получение заказов

HTTP:
  GET {Адрес}/Order/Order/getOrders?bilUserLogin=<Логин>&bilUserPassword=<Пароль>&starts=<дата>

Логин/пароль — поля Логин и Пароль настроек (не FTP).
starts — нижняя граница выборки, дата ISO с локальным смещением.
Символ «+» в смещении заменяется на %2B.

Граница:
  Константа эв_ДатаУспешнойзагрузкиЗаказовАтекаМос
  (в имени константы опечатка: «Атека», без «п»).
  Фактически: Макс(Константа, дата '20250901').
  При HTTP 200 константа сразу записывается текущей датой запроса
  (до разбора заказов). Пустой список заказов тоже сдвигает границу.

Заголовок: Content-Type: application/json.
Фильтра по складу в URL нет: портал отдаёт заказы учётки, 1С отсекает
чужие аптеки по orgId.

Успех: HTTP 200, массив заказов в поле orders.
Пустой массив — норма.
Иной код — ЖР, константа не обновляется (обновление только в ветке 200).

4.2. Структура элемента orders (поля, которые читает 1С)

Заголовок:
  orgId            number   Id аптеки. Заказ обрабатывается, только если
                            orgId = Число(merchant). Иначе строка пропускается.
  orderNum         string   Номер заказа. Неразрывные пробелы (Символы.НПП) удаляются.
                            В 1С: НомерЗаказаНаСайте.
  orderTime        string   Дата ISO. Читается ПрочитатьДатуJSON(..., ISO).
  custFullName     string   ФИО. Разбор по пробелам:
                              1-е слово = Фамилия,
                              2-е = Имя,
                              3-е = Отчество.
                            (У МегаАптеки/Ютеки наоборот: 1-е = Имя, 2-е = Фамилия.)
  custEmail        string   Почта.
  custPhone        string   Телефон (нормализуется ПривестиТелефон).
  orderRealSum     number   Сумма заказа.
  custComment      string   Комментарий клиента.
  orderStatComment string   Комментарий к статусу.
  operComment      string   Комментарий оператора.
                            Три комментария склеиваются через перевод строки.

Строки — массив positions:
  itemId    string/number  И идентификатор позиции, и xmlId номенклатуры.
                           В 1С: xmlId = itemId, эвИдПозиции = itemId.
  qtty      number         Количество.
  price     number         Цена.
  itemName  string         Наименование.

Сырой объект заказа сохраняется в ЗаказПокупателя.Этикетка.
Для частичной сборки строки читаются из Этикетка.positions (itemId, qtty).

Обработка входящих статусов отмены/подтверждения клиента в текущем коде закомментирована.
Повторно пришедший заказ с тем же orderNum только попадает в список загруженных
и снова ставится в очередь как «Новый».

4.3. Создание документа

Идемпотентность: поиск по НомерЗаказаНаСайте = orderNum и тому же источнику.
Если найден — не пересоздаётся, добавляется в ИДЗагруженных.

Если нет:
  1) Документ ЗаказПокупателя.
  2) Контрагент по email+телефон+фамилия+имя+отчество.
  3) Товары через ОбменССайтомСобытия.ЗагрузитьТоварыЗаказа
     (xmlId/эвИдПозиции = itemId).
  4) Шапка: организация/магазин/склад источника, ИнтернетЗаказ, НДС,
     статус Согласован, эвИсточникЗаказа = АптекаМос.
  5) Запись с ОбменДанными.Загрузка, затем проведение.
  6) Локальный статус «Новый», оплата НеОплачен, доставка НеСобран.

После цикла по orders каждый элемент ИДЗагруженных (и новые, и уже существовавшие)
ставится в очередь:
  СтатусЗаказа   = Новый
  СтатусОтправки = КПередаче

Запись в очередь проверяет ОчередностьСтатусовКорректна. Переход «в Новый»
с уже продвинутого статуса отдельным запретом не закрыт — в целевой реализации
лучше не копировать повторную постановку существующих заказов в «Новый».


================================================================================
5. ОТПРАВКА СТАТУСОВ ЗАКАЗОВ
================================================================================

Процедура: ОтправитьСтатусЗаказаАптекаМос

HTTP:
  POST {Адрес}/Order/Order/setOrders

Комментарий в коде (контракт портала):

  bilUserLogin     — логин
  bilUserPassword  — пароль
  params[]:
    orderNum         — внутренний id заказа (можно orderNum и/или orderExtNum)
    orderExtNum      — внешний id (в 1С не передаётся)
    orderStat        — внутренний статус заказа на портале
    orderExtStatId   — код внешнего статуса, приоритетнее orderStat (в 1С не передаётся)
    orderStatComment — комментарий к статусу (в 1С не передаётся)
    orderRealSum     — реальная стоимость
    orderAttr        — атрибуты (в 1С не передаётся)

Фактически 1С отправляет:

{
  "bilUserLogin": "<Логин>",
  "bilUserPassword": "<Пароль>",
  "params": [
    {
      "orderNum": "<НомерЗаказаНаСайте>",
      "orderStat": "<эвВидыСтатусовЗаказов.АптекаМос>",
      "orderRealSum": 498.00
    }
  ]
}

Логин/пароль — поля Логин и Пароль (не FTP).
orderStat — строковый реквизит АптекаМос элемента справочника статусов,
а не числовой Код (Код используется МегаАптекой/Ютекой).
Значения реквизита в выгрузке метаданных предопределённых элементов нет —
их нужно взять из рабочей базы (в комментарии API встречаются TRANSFERRED, az_new).

Успех: HTTP 200 → очередь «Отправлен», локальный статус фиксируется.
Иначе → очередь «Ошибка», повтор до 20 попыток.

Частичная сборка: ВернутьТоварыПоЗаказуДляПортала для АптекаМос собирает
{ id: itemId, quantity: факт }, но в setOrders массив позиций сейчас не передаётся.
В целевой реализации уточнить у портала, нужен ли состав в orderAttr / отдельном поле.

6. ПРИМЕРЫ ЗАПРОСОВ
================================================================================

6.1. Полная выгрузка остатков

POST /Price/WPrice/WimportPrices
Headers:
  Content-Type: application/json

{
  "bilUserLogin": "ftp_login",
  "bilUserPassword": "ftp_password",
  "isTransact": 0,
  "prices": [
    {
      "org_id": "1001",
      "drug_id": 12345678,
      "item_id": "b1c2d3e4-aaaa-bbbb-cccc-ddddeeeeffff",
      "item_name": "Нурофен 200 мг №20",
      "item_code": "01.03.2027",
      "price": 249,
      "qtty": 12,
      "reserv": 1
    }
  ]
}

Ожидаемый ответ: HTTP 200.

6.2. Инкрементальная выгрузка остатков

POST /Price/WPrice/WimportPrices
Тело как в 6.1, но "isTransact": 1.
В prices только изменившиеся позиции, включая qtty = 0.

6.3. Получение заказов

GET /Order/Order/getOrders?bilUserLogin=api_login&bilUserPassword=api_pwd&starts=2025-09-01T00:00:00%2B03:00

Пример успешного тела (поля, которые читает 1С):

{
  "orders": [
    {
      "orgId": 1001,
      "orderNum": "210903964",
      "orderTime": "2026-09-29T10:15:00+03:00",
      "custFullName": "Петров Иван Сергеевич",
      "custEmail": "ivan@example.com",
      "custPhone": "79001234567",
      "orderRealSum": 498,
      "custComment": "позвонить за 10 минут",
      "orderStatComment": "",
      "operComment": "",
      "positions": [
        {
          "itemId": "b1c2d3e4-aaaa-bbbb-cccc-ddddeeeeffff",
          "qtty": 2,
          "price": 249,
          "itemName": "Нурофен 200 мг №20"
        }
      ]
    }
  ]
}

6.4. Отправка статуса (в том числе «новый заказ получен»)

POST /Order/Order/setOrders

{
  "bilUserLogin": "api_login",
  "bilUserPassword": "api_pwd",
  "params": [
    {
      "orderNum": "210903964",
      "orderStat": "TRANSFERRED",
      "orderRealSum": 498
    }
  ]
}

Ожидаемый ответ: HTTP 200.
Конкретные строки orderStat взять из реквизита АптекаМос справочника статусов рабочей базы.


================================================================================
7. ОТЛИЧИЯ ОТ МЕГААПТЕКИ / ЮТЕКИ
================================================================================

                          МегаАптека / Ютека                 АптекаМос
  Авторизация             token + merchant                   login/password в query или теле
  Учётки                  одни на всё                        Логин/Пароль — заказы и статусы;
                                                             ЛогинФТП/ПарольФТП — остатки
  Id аптеки               store_id = UUID склада             org_id / orgId = merchant (число)
  Id товара               UUID номенклатуры                  drug_id = ЕГК + item_id = UUID
  Штрихкоды               передаются                         не передаются
  Полные остатки          POST /prices                       POST .../WimportPrices, isTransact=0
  Инкремент               POST или PUT /prices               POST .../WimportPrices, isTransact=1
  Заказы                  GET /orders                        GET .../getOrders?starts=
  Подтверждение           POST /orders/exported              нет; статус «Новый» через setOrders
  Статусы                 POST /orders, status_id число      POST .../setOrders, orderStat строка
  Граница заказов         нет (портал отдаёт новые)          константа даты + starts
  ФИО                     имя, фамилия                       фамилия, имя, отчество


================================================================================
8. ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ В ДРУГОЙ КОНФИГУРАЦИИ
================================================================================

Обязательный минимум:

1) Настройки: URL, Логин, Пароль, ЛогинФТП, ПарольФТП, merchant (org_id), склад, вид цены.
2) Реквизит номенклатуры с кодом ЕГК (аналог ор_ЕГК). Без него позиция не выгружается.
3) Регистр-снимок остатков (ключ номенклатура + характеристика/серия).
4) POST /Price/WPrice/WimportPrices:
     isTransact=0 полная, isTransact=1 инкремент;
     credentials = ЛогинФТП/ПарольФТП.
5) Не выгружать позиции с ценой 0 или пустым ЕГК.
6) GET /Order/Order/getOrders с starts и credentials Логин/Пароль.
7) Хранить границу успешного запроса; не сдвигать её при ошибке HTTP.
8) Отбирать заказы по orgId = merchant.
9) Идемпотентность по orderNum.
10) Сохранять сырой JSON (positions.itemId) для возможных статусов сборки.
11) POST /Order/Order/setOrders для статусов; маппинг локальный статус → строка orderStat.

Рекомендуется:
12) Не ставить повторно в очередь «Новый» уже существующие заказы.
13) Проверять заполненность URL и FTP-учётки, не только Логин/Пароль/merchant.
14) Не класть пароль в URL в логах; в query он всё же уходит (так устроен API).
15) Уточнить у портала актуальные значения orderStat и необходимость состава заказа.
16) В запросе цен явно выбирать ЦеновуюГруппу (дефект исходника).

Особенности, которые нельзя потерять:

  - Две разные пары логин/пароль: заказы/статусы vs остатки.
  - isTransact, а не разные HTTP-методы, отличает полную выгрузку от инкремента.
  - drug_id = ЕГК, item_id = UUID 1С; оба поля обязательны в пакете цен.
  - item_code используется как срок годности dd.MM.yyyy.
  - reserv всегда 1.
  - ФИО: фамилия-имя-отчество, не имя-фамилия.
  - Нет /orders/exported.
  - Код статуса — строка АптекаМос, не числовой Код справочника.

ОПИСАНИЕ API ПОРТАЛА ЮТЕКА
Назначение файла: исходные данные для промта на реализацию обмена в другой конфигурации 1С.
Дата сборки: 2026-09-29.

В заказе покупателя есть поле ВидЗаказа. Для каждого портала будет создан свой вид заказа. В нем мы укажем 
поле Портал с типом перечисление эв_ВидыИсточниковЗаказа.
В виде заказа будет прописан перечен Статусов заказов а табличной части Состояния. 

Состояния заказов имеют код на партале. На каждом портале свой код статуса. 
Связь состояний заказа и значений кодов статусов заказа на портале задаются в регистре сведений: эв_КодыСтатусовПорталов,
где ВидСтатуса это состояние заказа покупателя. И вид источника заказа.

Результаты каждого HTTP запроса фиксируются в регистре сведений эв_ЛогиHTTPПорталов.
Сборка пакета остатков и разбор JSON заказа общие с МегаАптекой.
Отличия Ютеки — авторизация, query-параметр mc, HTTP-методы выгрузки остатков и отсутствие разбора success_ids.


================================================================================
1. ОБЩИЕ СВЕДЕНИЯ
================================================================================

Портал: Ютека (перечисление эв_ВидыИсточниковЗаказа.Ютека).

Сценарии, которые нужно реализовать:
1) Полная выгрузка остатков и цен.
2) Инкрементальная выгрузка остатков и цен (только изменения).
3) Загрузка заказов с портала и подтверждение получения.

Смежный сценарий (не запрошен явно, но нужен для замкнутого цикла заказов):
4) Отправка статусов заказов на портал.

Базовый URL, токен и код мерчанта хранятся в регистре сведений эвНастройкиAPIИсточникаЗаказов
в разрезе источника заказов (справочник эвИсточникиЗаказов):
  - Адрес       — базовый URL API без завершающего слэша, например https://api.example.com
  - auth_token  — токен авторизации (уходит в заголовок auth_token)
  - merchant    — код мерчанта (уходит в query-параметр mc, не в заголовок)

Источник заказов (справочник эвИсточникиЗаказов) для Ютеки должен содержать:
  - Вид      = Ютека
  - Активный = Истина
  - Склад    — склад аптеки (его UUID уходит в API как store_id)
  - ВидЦен   — вид цены, которым заполняется price

Проверка готовности настроек (ДанныеПорталаКорректны):
  Адрес, auth_token и merchant не должны быть пустыми.

Формат обмена: JSON, кодировка UTF-8.
Content-Type: application/json

Идентификаторы:
  - store_id  — UUID склада 1С (XMLСтрока(Склад), 36 символов).
  - id товара — UUID номенклатуры 1С (XMLСтрока(Номенклатура)), НЕ характеристики.
  - id заказа — числовой external_id портала.
  - mc        — код мерчанта из настроек (СокрП в выгрузке остатков и GET /orders).


================================================================================
2. АВТОРИЗАЦИЯ (заголовки и query для всех запросов Ютеки)
================================================================================

Заголовки:
  Content-Type: application/json
  auth_token:   <auth_token>

Query (добавляется ко всем URL Ютеки, кроме тела JSON):
  mc=<merchant>

Важно:
  - Имя заголовка с подчёркиванием: auth_token. Не auth-token.
  - Заголовка merchant-code у Ютеки нет. Код мерчанта только в query mc=.
  - У МегаАптеки наоборот: заголовки merchant-code и auth-token, query mc не используется.

Примеры URL:
  POST {Адрес}/prices?mc=MERCHANT
  PUT  {Адрес}/prices?mc=MERCHANT
  GET  {Адрес}/orders?mc=MERCHANT&store_id=<UUID>
  POST {Адрес}/orders/exported?mc=MERCHANT
  POST {Адрес}/orders?mc=MERCHANT


================================================================================
3. РЕГЛАМЕНТ И ТОЧКИ ВХОДА В 1С
================================================================================

2.1. Инкрементальные остатки + загрузка заказов
Регламентное задание: эв_ОбменОстаткамиИЗаказамиПорталов
Метод: эв_ОбменСПорталамиСервер.ВыполнитьИнкрементальныйОбмен
Расписание метаданных: каждые 120 секунд, с 08:00 до 23:30.
Выполняется только на боевой базе.

Порядок:
  1) эв_ОбменСПорталамиСервер.ВыполнитьИнкрементальныйОбмен → внутри ВыполнитьЗагрузкуЗаказовИзЮтека()
  2) эв_ВыгрузитьОстаткиЦеныНаПорталЮтека(Ложь)

2.2. Полные остатки
Регламентное задание: эв_ОбменОстаткамиПолнымиПорталов
Метод: эвОбменСПорталамиСобытия.ВыполнитьОбменСПорталамиПолная
Расписание метаданных: 23:35–23:45.
Вызов: эв_ВыгрузитьОстаткиЦеныНаПорталЮтека(Истина)

2.3. Очередь статусов
Регламентное задание: эв_ОбработкаОчередиСтатусовПорталов
Метод: ВыполнитьОбработкуОчередиСтатусовПорталов → ОтправитьСтатусЗаказаЮтека
Расписание: каждые 30 секунд, с 08:00 до 23:00.

Код статуса для портала берётся в регистре сведений: эв_КодыСтатусовПорталов,
Статусы отправляются через очередь в регистре эв_ОчередьОтправкиСтатусовЗаказов.

Текущий статус при успешной отправке на портал фиксируется в регистре эв_ИсторияСтатусовЗаказов.



================================================================================
4. ВЫГРУЗКА ОСТАТКОВ И ЦЕН
================================================================================

Сборка list общая с МегаАптекой. Отличие Ютеки — HTTP-метод и query mc.

HTTP:
  полная выгрузка:        POST {Адрес}/prices?mc=<merchant>
  инкрементальная:        PUT  {Адрес}/prices?mc=<merchant>

merchant в URL берётся через СокрП (обрезаются пробелы справа).

В теле по-прежнему передаётся is_full: true/false, хотя полнота уже выражена методом POST/PUT.

4.1. Тело запроса

{
  "store_id": "<UUID склада>",
  "is_full": true | false,
  "list": [
    {
      "id": "<UUID номенклатуры>",
      "barcodes": ["4600000000000", "4600000000001"],
      "name": "Наименование номенклатуры",
      "brand_name": "Производитель",
      "price": 199,
      "available_count": 5,
      "expires": "2026-12-31",
      "series": "A123"
    }
  ]
}

Поля позиции list:

  id               string   UUID номенклатуры 1С. Одна номенклатура может встретиться в list
                            несколько раз (разные характеристики/серии/сроки годности).
  barcodes         array    Массив штрихкодов EAN-12/EAN-13.
  name             string   Представление номенклатуры.
  brand_name       string   Представление производителя (Номенклатура.ор_Производитель).
                            Если производитель не заполнен — пустая строка.
  price            number   Цена целым числом (приведение ЧИСЛО(10, 0), дробная часть отбрасывается).
                            Берётся из регистра ЦеныНоменклатуры по виду цен источника.
                            Сначала цена с характеристикой, если нет — цена без характеристики.
  available_count  number   Целая часть доступного остатка: КоличествоОстаток − РезервОстаток.
  expires          string   Срок годности характеристики, формат yyyy-MM-dd
                            (Характеристика.ор_СрокГодности). Если дата пустая, 1С отправит
                            пустую/нулевую дату в этом формате.
  series           string   Серия производителя (Характеристика.ор_СерияПроизводителя), СокрП.

4.2. Сбор штрихкодов (barcodes)

Источники, объединяются без дублей:

  1) РС Штрихкоды по владельцу = номенклатура:
     - характеристика пустая;
     - длина штрихкода 12 или 13 символов.
  2) Справочник ШтрихкодыУпаковокТоваров (тип GS1_DataMatrix),
     связанный по номенклатуре+характеристике:
     - EAN = ПОДСТРОКА(ЗначениеШтрихкода, 6, 13).
  3) Справочник ор_МДЛПУпаковкиМаркируемыхТоваров,
     связанный по номенклатуре+характеристике:
     - EAN = ПОДСТРОКА(НомерУпаковки, 2, 13).

4.3. Отбор строк, которые уходят на портал

Доступный остаток считается по складу источника:
  ТоварыНаСкладах.Остатки: КоличествоОстаток − РезервОстаток >= 1.

Фильтр перед отправкой:
  Если Цена = 0 И ДоступныйОстаток <> 0 — строка НЕ отправляется.
  (Позиция с ненулевым остатком и нулевой ценой на портал не выгружается.)
  Позиция с нулевым остатком отправляется (нужна, чтобы обнулить остаток на портале).

Если после сборки list пустой — HTTP-запрос не выполняется.

4.4. Полная выгрузка (is_full = true, метод POST)

Состав list: все позиции склада с доступным остатком >= 1 (и прошедшие фильтр цены).

После HTTP 200:
  1) Регистр эв_СвободныеОстаткиДляПорталаЮтека очищается полностью.
  2) Заново записываются только строки с ДоступныйОстаток <> 0:
       измерения: Номенклатура, Характеристика
       ресурсы:   ДоступныйОстаток, Цена
       реквизит:  ДатаОбновления = текущая дата.

4.5. Инкрементальная выгрузка (is_full = false, метод PUT)

Сравнение текущего учёта со снимком последней успешной выгрузки
(регистр эв_СвободныеОстаткиДляПорталаЮтека):

  Выгружаются только пары (Номенклатура, Характеристика), у которых
  остаток в снимке <> текущему доступному остатку учёта.

  Это покрывает:
    - появление нового остатка;
    - изменение количества;
    - обнуление (позиция исчезла из учёта, в снимке ещё была) —
      в list уходит available_count = 0.

После HTTP 200 снимок обновляется точечно по выгруженным ключам:
  - если ДоступныйОстаток <> 0 — запись перезаписывается;
  - если ДоступныйОстаток = 0 — запись по ключу удаляется (набор записей очищается).

4.6. Успех и ошибки

Успех: HTTP 200. Только после 200 обновляется регистр-снимок.
Иначе снимок не трогается, при следующей итерации те же изменения уйдут снова.

Ошибка: любой код кроме 200. В журнале регистрации пишется код и тело ответа (СтрокаJson).
Исключение транспорта тоже пишется в ЖР, пакет не считается успешным.
Если ответа нет (не структура) — в ЖР пишется «Нет ответа».

4.7. Регистр-снимок эв_ВыгруженныеОстаткиПорталов

Непериодический, независимый.
Измерения: Номенклатура, Характеристика.
Ресурсы:   Цена (15.2, неотрицательное), ДоступныйОстаток (15.3).
Реквизит:  ДатаОбновления (дата и время).

Назначение: хранить, что уже ушло на портал, чтобы инкремент слал только дельту.


================================================================================
5. ЗАГРУЗКА ЗАКАЗОВ
================================================================================

Процедура: ВыполнитьЗагрузкуЗаказовИзПорталов.
Обход: по активным источникам вида Ютека, по каждому складу источника.
Разбор JSON общий с МегаАптекой (ЗагрузитьЗаказыJSON). Отличие — URL получения заказов.

5.1. Получение новых заказов

HTTP:
  GET {Адрес}/orders?mc=<merchant>&store_id=<UUID склада>

merchant — СокрП(Источник.merchant).
store_id — XMLСтрока(Склад), без JSON-обёртки.

Это не МегаАптека: там GET /orders?data={"store_id":"..."} без mc.

Заголовки:
  Content-Type: application/json
  auth_token:   <auth_token>

Успех: HTTP 200, массив заказов в поле list.
Пустой list — норма, обработка склада пропускается.
Иной код — ошибка в ЖР (код + тело), переход к следующему источнику/складу.

5.2. Структура элемента list (поля, которые читает 1С)

Заголовок заказа:
  external_id     number/string  Номер заказа на портале. В 1С: НомерЗаказаНаСайте.
                                 При подтверждении приводится к Число.
  status_id       number         Статус на портале. Используются как минимум:
                                   3 — отменён на сайте;
                                   8 — подтверждён клиентом.
  creation_date   number         Unix-время. В 1С: Дата = '19700101' + creation_date + 10800
                                 (сдвиг +3 часа, Москва).
  fio             string         ФИО. Разбор: 1-е слово = Имя, 2-е = Фамилия (разделитель пробел).
  email           string         Электронная почта покупателя.
  phone           string         Телефон (нормализуется локальной функцией ПривестиТелефон).
  amount          number         Сумма заказа.
  message         string         Комментарий заказа.

Строки заказа — массив items:
  id              number         Идентификатор позиции на портале. В 1С сохраняется
                                 в строке заказа как эвИдПозиции. Нужен для частичной сборки.
  item_id         string         UUID/код товара на стороне аптеки (xmlId номенклатуры).
  quantity        number         Количество.
  price           number         Цена.
  item_name       string         Наименование позиции.

Исходный JSON заказа целиком сохраняется в документе ЗаказПокупателя.Этикетка
(ХранилищеЗначения). Позже из Этикетка.items читаются id / item_id / quantity
для отправки частичной сборки.

Другие поля ответа портала, если они есть, текущий код не разбирает, но сохраняет
в Этикетка вместе со всем объектом заказа.

5.3. Логика создания / обновления заказа (ЗагрузитьЗаказыJSON)

Поиск существующего заказа: по НомерЗаказаНаСайте = external_id и тому же источнику.

Если заказ уже есть:
  - status_id = 3 → закрыть заказ, снять резерв, статус «Отменён на сайте».
  - status_id = 8 → поставить в очередь статусов «Подтверждён клиентом»
    (на портал этот статус повторно не отправляется, только фиксируется локально).
  - заказ попадает в список успешно загруженных (для /orders/exported).

Если заказа нет:
  1) Создать документ ЗаказПокупателя.
  2) Найти/создать контрагента по email+телефон+имя+фамилия.
  3) Загрузить товары через ОбменССайтомСобытия.ЗагрузитьТоварыЗаказа:
       xmlId      = item_id
       quantity   = quantity
       price      = price
       name       = item_name
       эвИдПозиции = id позиции портала
  4) Заполнить шапку:
       Организация, Магазин, Склад — из источника заказов;
       Дата / ДатаЗаказаНаСайте / ЖелаемаяДатаПродажи = дата из creation_date;
       НомерЗаказаНаСайте = external_id;
       ИнтернетЗаказ = Истина;
       УчитыватьНДС = Истина;
       Статус документа = Согласован;
       Комментарий = message;
       эвИсточникЗаказа = источник Ютека.
  5) Записать (с ОбменДанными.Загрузка = Истина), затем провести.
     Ошибка проведения не блокирует подтверждение получения.
  6) Локальный статус заказа = «Новый».
  7) Оплата: НеОплачен, ОплаченНаСайте = Ложь.
  8) Доставка: состояние НеСобран, комментарий «##Загружено из <источник> <дата>».
  9) Уведомление клиента о новом заказе.

5.4. Подтверждение получения заказа

После разбора list вызывается ОтправитьОтметкуПолучения.

HTTP:
  POST {Адрес}/orders/exported?mc=<merchant>

Тело:
{
  "id": [123456, 123457]
}

Массив id — числовые external_id успешно разобранных заказов.
Заказы с признаком ЕстьОшибки в массив не включаются.
Пустой массив — запрос не отправляется.

Успех: HTTP 200.
Для Ютеки поле success_ids не разбирается: при 200 отметка считается принятой,
очередь повторной отправки не заполняется.

При коде отличном от 200:
  все загруженные заказы ставятся в очередь со статусом «Новый» и отправкой «Ошибка»,
  чтобы регламент очереди повторил POST /orders/exported?mc=...

Повтор из очереди статусов для статуса «Новый» — тот же контракт:
  POST {Адрес}/orders/exported?mc=<merchant>
  тело { "id": [ <НомерЗаказаНаСайте как число> ] }
  HTTP 200 → отправка считается выполненной.

Замечание по коду: в выгрузке остатков и GET /orders merchant обрезается СокрП,
в /orders/exported и /orders из очереди статусов — нет. В целевой реализации
лучше всегда нормализовать merchant (СокрЛП).


================================================================================
6. ОТПРАВКА СТАТУСОВ ЗАКАЗОВ (смежный API, для полноты цикла)
================================================================================

HTTP:
  POST {Адрес}/orders?mc=<merchant>

Тело совпадает с МегаАптекой:

{
  "list": [
    {
      "id": 123456,
      "status_id": 5,
      "cancel_reason": "нет товара",
      "reservation_end_date": 1760000000,
      "items": [ { "id": 1, "quantity": 2 } ]
    }
  ]
}

Поля элемента list:
  id                    number  НомерЗаказаНаСайте (число). Обязательно.
  status_id             number  Код статуса портала (см. таблицу ниже). Обязательно.
  cancel_reason         string  Только для статуса 3 (Отменён). Берётся из КомментарийМагазина.
  reservation_end_date  number  Только для статуса 5 (Готов к выдаче).
                                Unix UTC: ДатаОкончанияРезерва − '19700101' − 10800.
                                Если дата пустая — 0.
  items                 array   Только для статуса 7 (ожидает подтверждения из-за частичной сборки).
                                Элемент: { "id": <id позиции портала, число>, "quantity": <факт в заказе> }.
                                quantity — фактическое (не отменённое) количество по эвИдПозиции.

Успех: HTTP 200.
Ошибка: поле message, опционально массив errors (элемент — строка или структура с message).

Статус 8 «Подтверждён клиентом» на портал не отправляется: он приходит входящим
и только квитируется локально.

Таблица статусов (справочник эвВидыСтатусоэв_КодыСтатусовПорталов, ресурс КодПортала):

  Код  Имя в 1С                          Куда
  1    Новый                             POST /orders/exported?mc= (не /orders)
  2    Выдан                             POST /orders?mc=
  3    Отменён                           POST /orders?mc= + cancel_reason
  5    Готов к выдаче                    POST /orders?mc= + reservation_end_date
  7    Ожидает подтверждения клиентом    POST /orders?mc= + items
  8    Подтверждён клиентом              входящий status_id, локально
  9    Отменён на сайте                  входящий status_id=3, локально
  10   Отменён резерв                    локально (автоснятие резерва)

Очередь: РС эв_ОчередьОтправкиСтатусовЗаказов.
Повтор до 20 попыток, пока статус отправки не «Отправлен».

================================================================================
9. ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ В ДРУГОЙ КОНФИГУРАЦИИ
================================================================================

Обязательный минимум:

1) Хранение настроек: базовый URL, auth_token, merchant (mc), склад, вид цены.
2) Регистр-снимок последних успешно выгруженных остатков (ключ: номенклатура + характеристика
   или аналог серии/срока, если в целевой конфигурации нет характеристик аптечной розницы).
3) Полная выгрузка POST /prices?mc= с is_full=true: все ненулевые доступные остатки с ценой > 0.
4) Инкрементальная выгрузка PUT /prices?mc= с is_full=false: только дельта, включая нули.
5) Не выгружать позиции с остатком > 0 и ценой 0.
6) id товара = стабильный UUID/код номенклатуры, который портал потом вернёт в items.item_id.
7) store_id = стабильный UUID склада, согласованный с кабинетом Ютеки.
8) GET /orders?mc=&store_id=, создание заказа покупателя, идемпотентность по external_id.
9) POST /orders/exported?mc= после успешного разбора.
10) Сохранение сырого JSON заказа и id строк портала — без этого нельзя отправить статус 7.

Рекомендуется также:
11) Очередь исходящих статусов и POST /orders?mc=.
12) Обработка входящих status_id 3 и 8 при повторной загрузке того же заказа.
13) Журналирование HTTP-кода и тела ответа при коде <> 200.
14) Работа только в рабочей (боевой) базе либо явный переключатель.
15) Всегда trim merchant перед подстановкой в mc=.

Особенности, которые нельзя потерять при переносе:

  - Для Ютеки полная и инкрементальная выгрузки — разные HTTP-методы (POST vs PUT)
    на один URL /prices?mc=. В теле всё равно передаётся is_full.
  - Заголовок auth_token с подчёркиванием, без merchant-code.
  - Цена на портал — целое число.
  - Время: входящий creation_date — unix, плюс 3 часа; исходящий reservation_end_date —
    unix минус 3 часа (Москва, UTC+3).
  - Штрихкоды собираются с номенклатуры и дополнительно вырезаются из DataMatrix/МДЛП.
  - Одна номенклатура может дать несколько элементов list (разные серии/сроки).
  - Подтверждение получения и смена статуса — разные URL (/orders/exported vs /orders),
    оба с ?mc=.
  - При HTTP 200 на /orders/exported Ютека не использует success_ids.

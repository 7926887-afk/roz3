ОПИСАНИЕ API ПОРТАЛА АСНА (для промпта реализации в другой конфигурации)
================================================================================
Назначение файла: исходные данные для промта на реализацию обмена в другой конфигурации 1С.
Дата сборки: 2026-09-29.

В заказе покупателя есть поле ВидЗаказа. Для каждого портала будет создан свой вид заказа. В нем мы укажем 
поле Портал с типом перечисление эв_ВидыИсточниковЗаказа.
В виде заказа будет прописан перечен Статусов заказов а табличной части Состояния. 

Состояния заказов имеют код на партале. На каждом портале свой код статуса. 
Связь состояний заказа и значений кодов статусов заказа на портале задаются в регистре сведений: эв_КодыСтатусовПорталов,
где ВидСтатуса это состояние заказа покупателя. И вид источника заказа.

Результаты каждого HTTP запроса фиксируются в регистре сведений эв_ЛогиHTTPПорталов.

Целевая формулировка для промпта:
  Реализовать клиент интеграции АСНА v5: OAuth2, связки sku↔nnt, POST полных остатков,
  PUT инкрементальных остатков, GET заказов с разбором headers/rows/statuses.


================================================================================
0. РЕГЛАМЕНТ И ТОЧКИ ВХОДА В ИСХОДНИКЕ
================================================================================

2.1. Инкрементальные остатки + загрузка заказов
Регламентное задание: эв_ОбменОстаткамиИЗаказамиПорталов
Метод: эв_ОбменСПорталамиСервер.ВыполнитьИнкрементальныйОбмен
Расписание метаданных: каждые 120 секунд, с 08:00 до 23:30.
Выполняется только на боевой базе.

Порядок:
  1) эв_ОбменСПорталамиСервер.ВыполнитьИнкрементальныйОбмен → внутри ВыполнитьЗагрузкуЗаказовИзАсна()
  2) эв_ВыгрузитьОстаткиЦеныНаПорталАсна(Ложь)

2.2. Полные остатки
Регламентное задание: эв_ОбменОстаткамиПолнымиПорталов
Метод: эвОбменСПорталамиСобытия.ВыполнитьОбменСПорталамиПолная
Расписание метаданных: 23:35–23:45.
Вызов: эв_ВыгрузитьОстаткиЦеныНаПорталАсна(Истина)

2.3. Очередь статусов
Регламентное задание: эв_ОбработкаОчередиСтатусовПорталов
Метод: ВыполнитьОбработкуОчередиСтатусовПорталов → ОтправитьСтатусЗаказаАсна
Расписание: каждые 30 секунд, с 08:00 до 23:00.

Код статуса для портала берётся в регистре сведений: эв_КодыСтатусовПорталов,
Статусы отправляются через очередь в регистре эв_ОчередьОтправкиСтатусовЗаказов.

Текущий статус при успешной отправке на портал фиксируется в регистре эв_ИсторияСтатусовЗаказов.

 Перед выгрузкой остатков:
    эв_ЗагрузитьСвязкиНоменклатурыАСНА()

Ожидается одна активная точка АСНА (комментарий в коде: «более одной записи быть не должно»).

1. НАСТРОЙКИ ПОДКЛЮЧЕНИЯ
================================================================================

Справочник эв_ИсточникиЗаказов (Активный, Вид = Асна):
  Склад, ВидЦен, Организация/Магазин берутся со склада.

Регистр сведений эв_НастройкиAPIИсточникаЗаказов (по источнику):

  Поле          Назначение в HTTP АСНА
  ------------  ----------------------------------------------------------
  Адрес         base URL API (НЕ SSO). Пример вида: https://host
  Логин         storeId во всех путях /v5/stores/{storeId}/...
                также client_id для SSO
  Пароль        client_secret для SSO
  auth_token    кэш Bearer access_token
  merchant      в АСНА это НЕ merchant-code, а дата/время получения токена
  АдресФТП      для каталога DBF, для HTTP остатков/заказов не используется
  ЛогинФТП      то же
  ПарольФТП     то же

Проверка ДанныеПорталаКорректны для Асна требует:
  Логин, Пароль, АдресФТП, ЛогинФТП, ПарольФТП.
Для реализации только HTTP-остатков и заказов реально нужны:
  Адрес, Логин, Пароль, auth_token.

Плейсхолдеры ниже:
  {base}    = СокрЛП(Адрес)
  {storeId} = Логин


================================================================================
2. АВТОРИЗАЦИЯ (обязательна для всех методов v5)
================================================================================

Процедура: эв_ПолучениеТокенаАСНА.

Метод: POST
URL:   https://sso.asna.cloud:5000/connect/token
SSO-хост зашит в коде, не берётся из поля Адрес.

Заголовки:
  Content-Type: application/x-www-form-urlencoded

Тело (form-urlencoded, НЕ JSON):
  client_id={Логин}&client_secret={Пароль}&grant_type=client_credentials

В исходнике: КоннекторHTTP.PostJson(url, , {Заголовки, Данные: строка form}).

Успех: HTTP 200
Используемое поле ответа:
  access_token  → сохранить в auth_token, вернуть как Bearer.

Ошибка: HTTP <> 200, в ответе поле error.

На каждый запрос v5:
  Content-Type: application/json
  Authorization: Bearer {access_token}

Правило 401 (во всех методах ниже):
  получить новый токен, повторить запрос ОДИН раз тем же методом и телом.

Особенность исходника при выгрузке остатков:
  после получения токена в первом заходе в заголовок может уйти старый
  Источник.auth_token (ещё не обновлённый в строке настроек в памяти).
  При реализации лучше всегда подставлять свежий access_token.

3. СВЯЗКИ НОМЕНКЛАТУРЫ sku ↔ nnt (предпосылка остатков и заказов)
================================================================================

Процедура: эв_ЗагрузитьСвязкиНоменклатурыАСНА.
Вызывается перед полной выгрузкой остатков.
Без nnt позиция в остатки не попадает; строки заказа ищутся по nnt.

Метод: GET
URL:   {base}/v5/references/goods_links?names=false
Заголовки: JSON + Bearer

Успех: HTTP 200, тело — JSON-МАССИВ (не объект).
В исходнике КоннекторHTTP при массиве может вернуть сразу Тип("Массив")
без свойства КодСостояния. HTTP 401 приходит структурой с КодСостояния.

Элемент массива (используемые поля):
  sku  строка UUID номенклатуры 1С
  nnt  число, код АСНА

Пропускать элементы, у которых sku не валидный UUID.

Хранение исходника: РС эв_СправочникСвязокНоменклатурыАСНА
  измерение Номенклатура (ссылка по UUID sku)
  ресурс    КодАСНА = nnt

Пример:
GET /v5/references/goods_links?names=false
Authorization: Bearer ...

[
  { "sku": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee", "nnt": 1234567 },
  { "sku": "11111111-2222-3333-4444-555555555555", "nnt": 7654321 }
]


================================================================================
4. ВЫГРУЗКА ОСТАТКОВ И ЦЕН
================================================================================

Процедура: эв_ВыгрузитьОстаткиЦеныНаПорталАсна(ПолнаяВыгрузка)
Данные:     эв_ПолучитьОстаткиЦеныНаПорталАсна(Склад, ВидЦен, ПолнаяВыгрузка)

4.1. Полная vs инкрементальная — ОДИН URL, РАЗНЫЙ HTTP-МЕТОД

  Полная:         POST {base}/v5/stores/{storeId}/stocks
  Инкрементальная: PUT  {base}/v5/stores/{storeId}/stocks

Тело JSON одинаковое.
Успех обоих: HTTP 202 (принято в обработку).
401 → обновить токен, повторить тем же методом.
Иной код → ошибка (в ЖР пишутся код и тело).

Смысл для портала:
  POST = полная перезаливка стока аптеки.
  PUT  = частичное обновление (дельта, включая обнуление qnt).

4.2. Тело запроса

{
  "date": "yyyy-MM-ddTHH:mm:ss+00:00",
  "stocks": [ {позиция}, ... ]
}

date в исходнике:
  Формат(ТекущаяДата(), "ДФ=yyyy-MM-ddTЧЧ:мм:сс+00:00")
  ISO локального «сейчас» с фиксированным суффиксом +00:00.

Элемент stocks[]:

  Поле         Тип      Откуда / правило
  -----------  -------  ------------------------------------------------
  prtId        string   UUID партии/характеристики:
                        если Характеристика заполнена → XMLСтрока(Характеристика)
                        иначе → XMLСтрока(Номенклатура)
  nnt          number   код АСНА из связки
  sku          string   XMLСтрока(Номенклатура) — UUID номенклатуры
  qnt          int      Цел(доступный остаток по складу)
  gnvls        bool     Номенклатура.ор_ЖНВЛС
  exp          string   НЕОБЯЗАТЕЛЬНО. Только если заполнен
                        Характеристика.ор_СрокГодности:
                        Формат(..., "ДФ=yyyy-MM-ddT00:00:00+00:00")
  prcOptNds    number   розничная цена, целое ЧИСЛО(10,0)
  prcRet       number   та же цена
  prcGnvlsMax  number   та же цена

Фильтр перед отправкой: пропуск, если Цена = 0 ИЛИ nnt = 0.
Если stocks пуст — HTTP-запрос НЕ выполняется.

Пример:
{
  "date": "2026-09-29T12:00:00+00:00",
  "stocks": [
    {
      "prtId": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
      "nnt": 1234567,
      "sku": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
      "qnt": 12,
      "gnvls": false,
      "exp": "2027-05-01T00:00:00+00:00",
      "prcOptNds": 499,
      "prcRet": 499,
      "prcGnvlsMax": 499
    }
  ]
}

4.3. Как исходник отбирает позиции (логика дельты — на стороне 1С)

Фактический остаток:
  РН ТоварыНаСкладах.Остатки(склад источника)
  КоличествоОстаток - РезервОстаток >= 1
  разрез: Номенклатура + Характеристика.

Снапшот последней УСПЕШНОЙ отправки:
  РС эв_СвободныеОстаткиДляПорталаАсна
  (Номенклатура, Характеристика, ДоступныйОстаток, Цена, ДатаОбновления)

Запрос — UNION ALL снапшота и учёта, группировка по номенклатуре+характеристике.
В пакет уходит ДоступныйОстаток = сумма учёта (текущий складской остаток).

ПОЛНАЯ (ПолнаяВыгрузка = Истина):
  все позиции с учётом >= 1, без HAVING.
  После HTTP 202: снапшот очищается целиком и перезаписывается текущими
  остатками. Запись с нулевым остатком не создаётся.

ИНКРЕМЕНТ (ПолнаяВыгрузка = Ложь):
  HAVING: сумма(снапшот) <> сумма(учёт).
  Попадают:
    - изменилось количество;
    - товар исчез со склада (учёт < 1, но был в снапшоте) → в пакете qnt = 0.
  После HTTP 202: точечно по попавшим позициям —
    остаток <> 0 записать, остаток = 0 удалить запись снапшота.

Цена: РС ЦеныНоменклатуры.СрезПоследних по ВидЦен источника, округление до целого.
Особенность Эвалар: для ценовой группы «ЭВАЛАР» цена берётся по пустой
характеристике, иначе — по характеристике остатка.

В другой конфигурации:
  POST/PUT — контракт портала.
  Дельта PUT собирается локально сравнением учёта со снапшотом последней
  успешной отправки. Портал сам снапшот не ведёт.


================================================================================
5. ЗАГРУЗКА ЗАКАЗОВ
================================================================================

Процедура: ВыполнитьЗагрузкуЗаказовИзАСНА
Разбор:     ЗагрузитьЗаказыАСНАJSON
Связки:     ДополнитьСтрокиНоменклатурой

5.1. Получение пакета заказов

Метод: GET
URL:   {base}/v5/stores/{storeId}/orders_exchanger?since={since}
Заголовки: JSON + Bearer

since:
  max(константа эв_ДатаУспешнойзагрузкиЗаказовАсна, 01.09.2025)
  ЗаписатьДатуJSON(..., ФорматДатыJSON.ISO, ВариантЗаписиДатыJSON.ЛокальнаяДатаСоСмещением)
  символ «+» в смещении заменить на %2B (URL-encoding).

Пример:
  {base}/v5/stores/STORE_ID/orders_exchanger?since=2026-09-29T10:00:00%2B03:00

Успех: HTTP 200.
В исходнике константа эв_ДатаУспешнойзагрузкиЗаказовАсна = ТекущаяДата()
ставится СРАЗУ после 200, до записи документов.

401 → новый токен, повтор GET.
Иной код → ошибка, пакет не разбирается.

Если headers — пустой массив, обработка не выполняется.

Подтверждение получения ОтправитьОтметкуПолученияАСНА в текущем коде
ЗАКОММЕНТИРОВАНО. Для загрузки достаточно GET.

5.2. Структура ответа GET (корневой JSON-объект)

КоннекторHTTP кладёт поля JSON в ту же структуру, что и КодСостояния.

  headers   массив шапок заказов
  rows      массив строк товаров
  statuses  массив статусов
Связь всех трёх: orderId.

headers[] — используемые поля:

  Поле     Назначение в 1С
  -------  ----------------------------------------------------------
  orderId  идентификатор заказа на портале
           → РС фтм_ХарактеристикиИнтернетЗаказа.orderId
  src      читается в ТЗ, в реквизиты документа явно не пишется
  num      номер на сайте → ЗаказПокупателя.НомерЗаказаНаСайте
           идемпотентность: ОбменССайтомСобытия.ВернутьЗаказы(массив num)
  date     ISO JSON → Дата / ДатаЗаказаНаСайте / ЖелаемаяДатаПродажи
           ПрочитатьДатуJSON(..., ФорматДатыJSON.ISO); ошибка → ТекущаяДата()
  name     ФИО: разбить по пробелу, 1-я часть Имя, 2-я Фамилия
  mPhone   телефон → ОбменССайтомСобытия.ПривестиТелефон

statuses[]:

  orderId
  status   числовой код АСНА
  cmnt     комментарий → ЗаказПокупателя.Комментарий

На шапку накладывается статус с тем же orderId (в цикле перезаписываются
status и cmnt; фактически остаётся последний).

rows[]:

  orderId
  rowId    id позиции → эвИдПозиции в табличной части товаров
  nnt      код АСНА → поиск в эвСправочникСвязокНоменклатурыАСНА
           найдено: Номенклатура из регистра
           не найдено: в поле Номенклатура кладётся сам nnt «как есть»
  qnt      количество
  prc      цена
Сумма заказа = сумма(qnt * prc) по строкам заказа.

Пример ответа:
{
  "headers": [
    {
      "orderId": "ord-001",
      "src": 1,
      "num": "A-100500",
      "date": "2026-09-29T09:15:00+03:00",
      "name": "Иван Иванов",
      "mPhone": "79001234567"
    }
  ],
  "rows": [
    {
      "orderId": "ord-001",
      "rowId": "row-1",
      "nnt": 1234567,
      "qnt": 2,
      "prc": 499.00
    }
  ],
  "statuses": [
    {
      "orderId": "ord-001",
      "status": 200,
      "cmnt": ""
    }
  ]
}

Известные коды status при загрузке (зашиты в модуле):
  111 — отмена на сайте. Если заказ с таким num уже есть у источника Асна —
        закрыть заказ / снять резерв (статус «ОтменёнНаСайте»), новый документ
        не создавать.
  200 — используется исходником как «заказ получен» при PUT статусов
        (см. раздел 6); при GET не обрабатывается отдельно.

5.3. Логика создания документа (поведение исходника)

Для каждого headers[]:
  1) Уже есть ЗаказПокупателя с тем же num и тем же источником Асна:
       если status = 111 → закрыть/снять резерв;
       документ не создавать;
       orderId всё равно попадает в список загруженных.
  2) Иначе создать ЗаказПокупателя:
       Организация, Магазин, Склад — из источника;
       эвИсточникЗаказа = Асна;
       ИнтернетЗаказ = Истина, УчитыватьНДС = Истина;
       Статус документа = Согласован;
       Контрагент — поиск/создание по телефону + имя + фамилия (эл.почта пустая);
       Товары через ОбменССайтомСобытия.ЗагрузитьТоварыЗаказа:
         xmlId        = Строка(nnt)
         quantity     = qnt
         price        = prc
         name         = ""
         эвИдПозиции  = rowId
         Номенклатура = из связки
       Этикетка = ХранилищеЗначения(весь JSON-ответ headers+rows+statuses)
         нужно для последующей работы со строками (отмены позиций);
       запись в режиме загрузки, затем попытка проведения;
       внутренний статус обмена «Новый»;
       фтм_ХарактеристикиИнтернетЗаказа: ОплаченНаСайте = Ложь, orderId;
       оплата = НеОплачен, доставка = НеСобран.
  3) По каждому загруженному заказу в очередь статусов ставится
     «Новый» / «КПередаче» (отправка на портал — отдельный контур).


================================================================================
6. СМЕЖНО: PUT СТАТУСОВ ТОГО ЖЕ РЕСУРСА (не запрашивалось, кратко)
================================================================================

Нужно знать, чтобы не перепутать с загрузкой.

Метод: PUT
URL:   {base}/v5/stores/{storeId}/orders_exchanger
Успех: HTTP 201

Минимум:
{
  "statuses": [
    {
      "statusId": "{новый UUID}",
      "orderId":  "{orderId портала, не num}",
      "storeId":  "{storeId = Логин}",
      "date":     "{ISO локальная дата со смещением, ЗаписатьДатуJSON ISO ЛокальнаяДатаСоСмещением}",
      "status":   200,
      "cmnt":     ""
    }
  ]
}

Если есть частично отменённые строки, добавляется rows:
  { "rowId": "<id позиции>", "qntUnrsv": <фактическое оставшееся количество> }
  (в исходнике qntUnrsv = количество, оставшееся в заказе, не величина отмены).

Коды статусов очереди: эвВидыСтатусовЗаказов.КодАсна (не стандартный Код справочника).
После загрузки исходник ставит в очередь статус «Новый»; PUT отметки 200
в ВыполнитьЗагрузкуЗаказовИзАСНА закомментирован.


================================================================================
7. СВОДКА HTTP ДЛЯ РЕАЛИЗАЦИИ
================================================================================

1) Токен
   POST https://sso.asna.cloud:5000/connect/token
   Content-Type: application/x-www-form-urlencoded
   client_id, client_secret, grant_type=client_credentials
   200 → access_token

2) Связки (нужны nnt)
   GET  {base}/v5/references/goods_links?names=false
   200 → [ {sku, nnt}, ... ]

3) Полные остатки
   POST {base}/v5/stores/{storeId}/stocks
   { "date": "...", "stocks": [{prtId,nnt,sku,qnt,gnvls,exp?,prcOptNds,prcRet,prcGnvlsMax}] }
   202

4) Инкрементальные остатки

9. ГОТОВЫЙ БЛОК ДЛЯ ПРОМПТА
================================================================================

Реализуй обмен с порталом АСНА API v5.

Авторизация: POST https://sso.asna.cloud:5000/connect/token
(application/x-www-form-urlencoded: client_id, client_secret, grant_type=client_credentials).
Все прочие запросы: Content-Type application/json, Authorization Bearer.
При HTTP 401 получить токен заново и повторить запрос один раз.
storeId = идентификатор аптеки, подставляется в путь /v5/stores/{storeId}/...
base URL API отдельный от SSO.

Связки товаров: GET {base}/v5/references/goods_links?names=false
→ массив {sku: UUID номенклатуры, nnt: код АСНА}. Без nnt товар на портал не выгружать.

Полные остатки (суточный цикл): POST {base}/v5/stores/{storeId}/stocks
Инкрементальные (часто): PUT того же URL.
Тело одинаковое:
{
  "date": "yyyy-MM-ddTHH:mm:ss+00:00",
  "stocks": [{
    "prtId": "<UUID характеристики либо номенклатуры>",
    "nnt": <код АСНА>,
    "sku": "<UUID номенклатуры>",
    "qnt": <целое количество, 0 если позиция исчезла>,
    "gnvls": <bool ЖНВЛС>,
    "exp": "<yyyy-MM-ddT00:00:00+00:00, только если есть срок годности>",
    "prcOptNds": <целая цена>,
    "prcRet": <та же цена>,
    "prcGnvlsMax": <та же цена>
  }]
}
Успех остатков: HTTP 202.
Не отправлять позиции с ценой 0 или nnt 0.
Инкремент на стороне 1С: сравнивать текущий свободный остаток склада со снапшотом
последней успешной отправки; в PUT включать только изменившиеся, включая qnt=0.
После 202 обновлять снапшот.

Заказы (часто): GET {base}/v5/stores/{storeId}/orders_exchanger?since={ISO с %2B вместо +}
Успех: HTTP 200.
Ответ: { headers[], rows[], statuses[] }, связь по orderId.
headers: orderId, src, num, date, name, mPhone.
rows: orderId, rowId, nnt, qnt, prc. Номенклатура по nnt из связок.
statuses: orderId, status, cmnt.
Идемпотентность по num. Если заказ уже есть и status=111 — отмена на сайте, не создавать заново.
Сохранять сырой JSON ответа вместе с заказом (нужен orderId и rowId).
PUT того же URL — отправка статусов (201), для загрузки не обязателен.

Не использовать контракты Мегааптеки/Ютеки/АптекаМос.
